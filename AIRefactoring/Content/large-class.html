Code Smell

Large Class

A Large Class (often referred to as a God Class or Monster Class) is a class that has accumulated too many fields, properties, methods, and responsibilities. It usually happens gradually as developers repeatedly add new features to an existing, central class instead of creating specialized new classes.

When a class attempts to do too much, code clarity vanishes. Developers working on unrelated features end up modifying the same file, leading to frequent merge conflicts, hidden state dependencies, and high risk of unexpected regression bugs.

Key Takeaways

  • Violates the Single Responsibility Principle (SRP) by managing multiple unrelated domain concerns.
  • Creates excessive coupling, making the class hard to understand, maintain, or mock in unit tests.
  • High risk of side effects where altering one field or method breaks completely unrelated functionality.
  • Significantly increases compilation times and causes constant source control merge conflicts.

When & How to Refactor

Refactor a Large Class when you notice distinct clusters of fields or methods that operate independently of the rest of the class:

  • Extract Class: Move a group of related fields and their associated methods into a new, dedicated class.
  • Extract Subclass / Interface: If parts of the class are only used in specific execution contexts or configurations, extract them into specialized subclasses or behind clean interfaces.
  • Extract Domain Component: Group utility methods, validation logic, or formatting code into separate service components.

Example / Usage

// BEFORE: A bloated User Account class handling profile data, authentication, and notification preferences
public class UserAccount
{
    // Profile Data
    public int UserId { get; set; }
    public string FirstName { get; set; }
    public string LastName { get; set; }

    // Authentication Data & Operations
    public string PasswordHash { get; set; }
    public string SecurityToken { get; set; }
    public bool ValidatePassword(string password) => /* Hash & Compare */ true;
    public void ResetPassword(string newPassword) { /* Reset Logic */ }

    // Notification Preferences & Operations
    public bool EmailNotificationsEnabled { get; set; }
    public bool SmsNotificationsEnabled { get; set; }
    public string PhoneNumber { get; set; }
    public void SendSmsAlert(string message) { /* Send SMS */ }
    public void SendEmailAlert(string message) { /* Send Email */ }
}

// AFTER (C#): Refactored by extracting distinct concerns into modular sub-components
public class UserProfile
{
    public int UserId { get; set; }
    public string FirstName { get; set; }
    public string LastName { get; set; }
}

public class UserAuthentication
{
    public string PasswordHash { get; set; }
    public string SecurityToken { get; set; }

    public bool ValidatePassword(string password) => /* Hash & Compare */ true;
    public void ResetPassword(string newPassword) { /* Reset Logic */ }
}

public class UserNotifier
{
    public bool EmailNotificationsEnabled { get; set; }
    public bool SmsNotificationsEnabled { get; set; }
    public string PhoneNumber { get; set; }

    public void SendSmsAlert(string message) { /* Send SMS */ }
    public void SendEmailAlert(string message) { /* Send Email */ }
}

// Composition container aggregating the extracted responsibilities
public class UserAccountRefactored
{
    public UserProfile Profile { get; set; } = new();
    public UserAuthentication Auth { get; set; } = new();
    public UserNotifier Notifier { get; set; } = new();
}
